# ข้อเสนอ: แยกขั้นตรวจ OTP ออกจากขั้นตั้งรหัสผ่านใหม่ (password reset)

จากฝั่ง frontend (`next-frontend-stock`) ถึงฝั่ง backend (`Go-Backend-Stock`)

## ปัญหา

ตอนนี้ `POST /api/v1/auth/password-reset/confirm` รับ `{challenge_id, otp, new_password}` ในคำขอเดียว ตรวจ OTP และเปลี่ยนรหัสพร้อมกัน frontend เลยตรวจไม่ได้ว่า OTP ถูกก่อนให้ผู้ใช้ตั้งรหัสผ่านใหม่

ผลที่เกิดกับผู้ใช้คือ ต้องกรอก OTP แล้วตั้งรหัสผ่านใหม่จนครบ ถึงจะรู้ว่า OTP ผิดหรือหมดอายุ ต้องย้อนกลับไปกรอกใหม่ และกรอกผิดนับเข้าโควตา 5 ครั้งของรหัสนั้นด้วย

## สิ่งที่เสนอ

เพิ่ม endpoint ตรวจ OTP อย่างเดียว แล้วให้ `confirm` รับ token จากขั้นนั้นแทน OTP

### 1) `POST /api/v1/auth/password-reset/verify`

ต้องมี `X-CSRF-Token` และ cookie `csrf_nonce` เหมือน endpoint อื่นของกลุ่มนี้

```json
// request
{ "challenge_id": "...", "otp": "123456" }

// 200
{ "reset_token": "<opaque>", "expires_in": 600 }
```

- OTP ผิด หมดอายุ ถูกใช้แล้ว หรือโควตาหมด ตอบ `400 invalid_reset` เหมือนเดิมทุกกรณี ไม่แยกสาเหตุ
- กรอกผิดนับเข้าโควตา 5 ครั้งต่อรหัสเหมือน `confirm` และใช้ rate limit ชุดเดียวกัน (20 ครั้ง/15 นาที/IP)
- ถ้า OTP ถูก ให้ใช้ OTP นั้นไป (ใช้ได้ครั้งเดียว) และออก `reset_token` ที่ใช้ได้ครั้งเดียวเช่นกัน

### 2) `POST /api/v1/auth/password-reset/confirm` รับ body แบบใหม่ได้อีกแบบ

```json
{ "reset_token": "<opaque>", "new_password": "..." }
```

- ตรวจกติการหัสผ่านเหมือนเดิม รวมถึงกฎ "ห้ามมีส่วนหน้า @ ของอีเมล" ที่ตรวจหลังยืนยันตัวตนแล้ว
- ถ้า `reset_token` ผิด หมดอายุ หรือใช้แล้ว ตอบ `400 invalid_reset`
- สำเร็จแล้วทำเหมือนเดิม คือ 204, ออกจากระบบทุกอุปกรณ์ และส่งอีเมลแจ้งเตือน
- body เดิม `{challenge_id, otp, new_password}` ควรใช้ได้ต่อ เพื่อไม่ให้ client เดิมพัง ซึ่งเข้ากับแนวทางเพิ่มของใหม่ใน v1 ตาม ADR-0011

## ข้อควรระวังด้านความปลอดภัย

- `reset_token` ควรเป็นค่า random ยาวพอ เก็บฝั่ง server เป็น hash ใช้ได้ครั้งเดียว อายุสั้น (เสนอ 10 นาที) และผูกกับ `challenge_id` เดิม
- ถ้ากำหนดให้ผูกกับ `csrf_nonce` ของ browser ด้วย token ที่หลุดไปจะใช้ข้าม browser ไม่ได้ (ฝั่ง backend ตัดสินว่าจะผูกหรือไม่)
- การขอ OTP ใหม่ (`request`) ควรทำให้ `reset_token` ที่ออกไปก่อนหน้าใช้ไม่ได้ เหมือนที่ทำกับ OTP เก่า
- `verify` ต้องไม่เผยว่ามีบัญชีอยู่หรือไม่ บัญชีที่ไม่มีอยู่ต้องได้ผลเหมือนกรอกรหัสผิด รวมถึงเวลาตอบไม่ควรต่างกันจนสังเกตได้
- ควรบันทึก audit event ของ `verify` ทั้งสำเร็จและไม่สำเร็จ เหมือนที่ทำกับ `confirm`

## งานฝั่ง backend

- handler + service ของ `verify` และเพิ่ม body แบบ `reset_token` ใน `confirm`
- ที่เก็บ `reset_token` (ตาราง/คอลัมน์ใหม่) พร้อม migration
- test: OTP ถูก/ผิด/หมดอายุ/ถูกใช้แล้ว/โควตาหมด, token ใช้ซ้ำ, token หมดอายุ, `request` ใหม่แล้ว token เก่าใช้ไม่ได้, `confirm` แบบเดิมยังทำงาน
- อัปเดต swagger annotations แล้ว generate เอกสารใหม่ รวมถึง `docs/frontend-handoff.md` (หัวข้อ 4 และ 7)

## ฝั่ง frontend หลังได้ endpoint นี้

หน้า "กรอก OTP" เรียก `verify` ก่อนไปหน้าตั้งรหัสผ่านใหม่ ถ้าผิดจะแสดง error ที่หน้า OTP ทันที ตอนนี้ UI แยกเป็นสองหน้าแล้ว จึงแก้แค่ตรงจุดที่เรียก API

## ทางเลือกอื่น

**ไม่เปลี่ยน backend:** ใช้ flow เดิมต่อ ผลคือผู้ใช้เห็นว่า OTP ผิดตอนกดปุ่มสุดท้ายเท่านั้น ข้อดีคือ backend มี endpoint น้อยกว่าและไม่มี token ใหม่ให้ดูแล ข้อเสียคือผู้ใช้อาจกรอกรหัสผ่านเสร็จแล้วต้องย้อนกลับ

## คำถามที่ต้องการให้ฝั่ง backend ตัดสิน

1. ต้องการ endpoint `verify` ไหม หรือคงแบบเดิม
2. `reset_token` อายุเท่าไร และผูกกับ `csrf_nonce` หรือไม่
3. `confirm` ต้องรองรับ body เดิมต่อหรือเลิกใช้

---

ข้อเสนอนี้ไม่เร่งด่วน เพราะ flow เดิมปลอดภัยและใช้งานได้ ที่เสนอมาเป็นเรื่องความสะดวกของผู้ใช้อย่างเดียว ถ้าฝั่ง backend มองว่าไม่คุ้มกับ endpoint ใหม่ UI สองหน้าตอนนี้ก็ใช้ต่อได้เลย
