# ข้อเสนอ: ข้อมูลสำหรับหน้า dashboard, เปอร์เซ็นต์กำไรขาดทุน, ราคาปัจจุบัน และกราฟเทียบดัชนี

จากฝั่ง frontend (`next-frontend-stock`) ถึงฝั่ง backend (`Go-Backend-Stock`)
เขียนเมื่อ 2026-11-10 สถานะ: รอฝั่ง backend ตัดสิน

## สรุป

เจ้าของโปรเจกต์อยากได้สี่อย่างในหน้าเว็บ ซึ่ง API ตอนนี้ยังให้ข้อมูลไม่พอ
frontend ถูกห้ามคำนวณต้นทุนและกำไรขาดทุนเอง จึงเสนอให้เพิ่มที่ backend
แต่ละข้อแยกตัดสินและแยกทำได้ ไม่ต้องรับทั้งชุด

| ข้อ | สิ่งที่ผู้ใช้อยากได้                                   | สิ่งที่ต้องเพิ่ม                                 | ขนาดงาน                          |
| --- | ------------------------------------------------------ | ------------------------------------------------ | -------------------------------- |
| A   | รู้ว่าหุ้นแต่ละตัวบวกหรือลบกี่ % และเป็นกี่ % ของพอร์ต | ฟิลด์ใหม่ใน `GET .../valuation`                  | เล็ก (เพิ่มฟิลด์ ไม่มีตารางใหม่) |
| B   | หน้า dashboard สรุปทุกพอร์ต พร้อมกราฟวงกลมสัดส่วนหุ้น  | endpoint สรุปรวมทุกพอร์ตของผู้ใช้                | กลาง                             |
| C   | ราคาปัจจุบันแทนราคาล่าช้า 15 นาที                      | ตัดสินใจเรื่องแหล่งราคา และบอกชนิดราคาใน `quote` | ขึ้นกับทางที่เลือก               |
| D   | กราฟเทียบผลตอบแทนพอร์ตกับ S&P 500 และ Nasdaq-100       | ราคารายวันย้อนหลัง และ endpoint ผลตอบแทนย้อนหลัง | ใหญ่ (งานของเฟสถัดไป)            |

ข้อ A และ B เป็นการเพิ่มของใหม่ใน v1 ตาม ADR-0011 ไม่เปลี่ยนของเดิม
ข้อ C แตะ ADR-0020 และข้อ D แตะ ADR-0012 จึงน่าจะต้องมี ADR ใหม่

## สิ่งที่ frontend ทำอยู่ตอนนี้

- หน้าพอร์ตแสดงตารางหุ้นที่ถือจาก `GET /portfolios/{id}/valuation`: จำนวน ต้นทุนเฉลี่ย ราคา มูลค่าตลาด
  และกำไรขาดทุนเป็นยอดเงิน USD โดยแสดงค่าที่ API ส่งมาตรงๆ ไม่คำนวณเพิ่ม
- ไม่มีคอลัมน์ % เพราะ API ไม่ส่ง และ frontend ไม่หารเอง
- ข้อความ "ราคาล่าช้าอย่างน้อย 15 นาที" เขียนตายตัวในหน้าเว็บ เพราะ `quote` ไม่มีฟิลด์บอกชนิดราคา
- หน้า dashboard ยังว่าง

## A. เปอร์เซ็นต์กำไรขาดทุนและสัดส่วนในพอร์ต

### ปัญหา

ผู้ใช้ถามว่า "ที่ซื้อมาบวกกี่ % ติดลบกี่ %" ตอนนี้ตอบได้แค่เป็นยอดเงิน
`PositionResponse` มี `unrealized_pnl` และ `cost_basis` แต่ไม่มีอัตราส่วนของสองค่านี้
และ `ValuationResponse` ไม่มีต้นทุนรวมของพอร์ต

### สิ่งที่เสนอ

เพิ่มฟิลด์ใน response ของ `GET /api/v1/portfolios/{portfolio_id}/valuation` ทุกค่าเป็น decimal string เหมือนฟิลด์อื่น

**ใน `PositionResponse`**

| ฟิลด์                    | ความหมาย                                     | เป็น `null` เมื่อ                                                  |
| ------------------------ | -------------------------------------------- | ------------------------------------------------------------------ |
| `unrealized_pnl_percent` | `unrealized_pnl / cost_basis × 100`          | `unrealized_pnl` เป็น `null` หรือ `cost_basis` เป็น 0 (ขายหมดแล้ว) |
| `weight_percent`         | `market_value / market_value ของพอร์ต × 100` | `coverage` ไม่ใช่ `complete`                                       |

**ใน `ValuationResponse`**

| ฟิลด์                    | ความหมาย                            | เป็น `null` เมื่อ                                     |
| ------------------------ | ----------------------------------- | ----------------------------------------------------- |
| `cost_basis`             | ผลรวมต้นทุนคงเหลือของหุ้นที่ยังถือ  | ไม่เป็น `null` (ไม่ขึ้นกับราคา)                       |
| `unrealized_pnl_percent` | `unrealized_pnl / cost_basis × 100` | `coverage` ไม่ใช่ `complete` หรือ `cost_basis` เป็น 0 |

ตัวอย่าง (ตัดฟิลด์เดิมออก):

```json
{
  "coverage": "complete",
  "cost_basis": "334.27",
  "market_value": "599.64",
  "unrealized_pnl": "265.37",
  "unrealized_pnl_percent": "79.39",
  "positions": [
    {
      "symbol": "AAPL",
      "cost_basis": "334.27",
      "market_value": "599.64",
      "unrealized_pnl": "265.37",
      "unrealized_pnl_percent": "79.39",
      "weight_percent": "100"
    }
  ]
}
```

### ข้อควรระวัง

- ค่าที่ไม่มีต้องเป็น `null` ห้ามเป็น `"0"` ตามหลักเดียวกับ ADR-0020: 0% อ่านได้ว่า "เท่าทุน" ซึ่งไม่จริง
- ชื่อฟิลด์ลงท้าย `_percent` และค่าเป็นหน่วยเปอร์เซ็นต์ (`"79.39"` คือ 79.39%) เพื่อไม่ให้สับสนกับอัตราส่วน `"0.7939"`
  ถ้าฝั่ง backend อยากส่งเป็นอัตราส่วน ขอให้ตั้งชื่อฟิลด์ให้ต่างกันชัดเจน
- ส่งค่าเต็มความละเอียดเหมือนฟิลด์อื่น การปัดเป็นหน้าที่ UI (จะแสดง 2 ตำแหน่ง)
- `weight_percent` ของหุ้นที่ขายหมดแล้ว: `market_value` เป็น `"0"` อยู่แล้ว จะให้เป็น `"0"` หรือ `null` ขอให้ฝั่ง backend เลือก

### ฝั่ง frontend หลังได้ฟิลด์เหล่านี้

- เพิ่มคอลัมน์ "% กำไร/ขาดทุน" และ "% ของพอร์ต" ในตารางหุ้นที่ถือ และช่อง "ต้นทุนรวม" ในยอดสรุป
- วาดกราฟวงกลมสัดส่วนหุ้นของพอร์ตจาก `weight_percent` ได้โดยไม่ต้องหารเอง

### ทางเลือกอื่น

**ให้ frontend หารเอง:** นำ `unrealized_pnl` หาร `cost_basis` และ `market_value` หารยอดพอร์ตด้วยไลบรารี decimal
ได้เห็นทันทีโดย backend ไม่ต้องทำอะไร แต่สูตรและกรณี `null` จะมีสองที่ และขัดกับข้อกำหนด
"frontend ไม่คำนวณ P&L เอง" จึงต้องให้เจ้าของโปรเจกต์อนุญาตเป็นข้อยกเว้นก่อน

## B. สรุปรวมทุกพอร์ตสำหรับหน้า dashboard

### ปัญหา

หน้า dashboard ต้องแสดงภาพรวมของผู้ใช้ทั้งบัญชี: มูลค่ารวม กำไรขาดทุนรวม ยอดของแต่ละพอร์ต
และกราฟวงกลมว่าถือหุ้นตัวไหนเป็นสัดส่วนเท่าไรเมื่อรวมทุกพอร์ต ตอนนี้ทำได้แค่เรียก `valuation` ทีละพอร์ต ซึ่งมีปัญหาสามข้อ

- frontend ต้องบวกยอดข้ามพอร์ตและรวมหุ้นตัวเดียวกันจากหลายพอร์ตเอง ซึ่งเป็นการคำนวณที่ไม่ควรอยู่ฝั่งเว็บ
- ผู้ใช้ที่มี N พอร์ตทำให้เกิด N คำขอต่อการเปิด dashboard หนึ่งครั้ง
- กติกา `coverage` เมื่อรวมหลายพอร์ต (พอร์ตหนึ่งราคาครบ อีกพอร์ตไม่ครบ) ต้องมีที่เดียวเป็นผู้ตัดสิน

### สิ่งที่เสนอ

endpoint ใหม่ เช่น `GET /api/v1/valuation` (ชื่อและ path ให้ฝั่ง backend เลือก) ต้องมี session เหมือน endpoint อื่น

```json
{
  "currency": "USD",
  "calculated_at": "2026-11-10T15:00:00Z",
  "coverage": "complete",
  "cost_basis": "1200",
  "market_value": "1500",
  "priced_market_value": "1500",
  "unrealized_pnl": "300",
  "unrealized_pnl_percent": "25",
  "realized_pnl": "40",
  "missing_symbols": [],
  "portfolios": [
    {
      "portfolio_id": "0192f0c1-...",
      "name": "Long term",
      "coverage": "complete",
      "cost_basis": "800",
      "market_value": "1000",
      "unrealized_pnl": "200",
      "unrealized_pnl_percent": "25",
      "realized_pnl": "40",
      "weight_percent": "66.67"
    }
  ],
  "allocation": [
    {
      "symbol": "AAPL",
      "instrument_name": "Apple Inc.",
      "quantity": "5",
      "market_value": "1000",
      "weight_percent": "66.67"
    }
  ]
}
```

- `allocation` รวมหุ้นตัวเดียวกันจากทุกพอร์ตเป็นแถวเดียว เรียงจากสัดส่วนมากไปน้อย ใช้วาดกราฟวงกลม
- กติกา `null` และ `coverage` เหมือน `valuation` ของพอร์ตเดียว: ยอดรวมเป็น `null` เมื่อราคาไม่ครบ
  และ `priced_market_value` เป็นผลรวมเฉพาะตัวที่มีราคา
- ผู้ใช้ที่ยังไม่มีพอร์ตหรือไม่มีรายการ ตอบ 200 พร้อมยอดเป็นศูนย์และ list ว่าง

### ข้อควรระวัง

- ราคาของ symbol เดียวกันควรดึงครั้งเดียวต่อคำขอ ไม่ใช่ครั้งละพอร์ต เพราะโควตา Alpaca 200 ครั้ง/นาที (ADR-0020)
- ถ้าผู้ใช้มีพอร์ตเกินจำนวนหนึ่ง ต้องตัดสินว่า `portfolios` จะแบ่งหน้าหรือจำกัดจำนวน
- ต้องไม่รวมพอร์ตของผู้ใช้อื่น และทดสอบกรณีนี้เหมือน endpoint อื่น

### ทางเลือกอื่น

**ไม่เพิ่ม endpoint:** dashboard แสดงการ์ดของแต่ละพอร์ตแยกกันโดยเรียก `valuation` ทีละพอร์ต
ไม่มียอดรวมทั้งบัญชีและไม่มีกราฟวงกลมรวม ทำได้ทันทีหลังข้อ A แต่ไม่ตรงกับ "สรุปภาพรวม" ที่เจ้าของโปรเจกต์ขอ

## C. ราคาปัจจุบันแทนราคาล่าช้า

### ปัญหา

เจ้าของโปรเจกต์ถามว่า "เปลี่ยนจากราคาล่าช้าเป็นราคาปัจจุบันไม่ดีกว่าหรือ"
frontend เปลี่ยนเองไม่ได้ เพราะแสดงราคาตามที่ API ส่งมา และข้อตกลงห้ามเรียกผู้ให้บริการราคาโดยตรง

ข้อจำกัดที่บันทึกไว้แล้วใน ADR-0020 และ `AGENTS.md`:

- Alpaca Basic (ฟรี) อ่าน SIP ได้เมื่อข้อมูลเก่ากว่า 15 นาที
- endpoint `latest`/snapshot ใช้ฟรีได้เฉพาะ feed IEX ซึ่งไม่ใช่ราคาตลาดรวม
- เฟสนี้ห้ามใช้บริการเสียเงิน และราคา live อยู่ในเฟสถัดไป (ADR-0012)

### ทางที่เป็นไปได้

| ทาง                     | ผู้ใช้เห็นอะไร                  | ข้อแลกเปลี่ยน                                                                                         |
| ----------------------- | ------------------------------- | ----------------------------------------------------------------------------------------------------- |
| 1. คงเดิม               | ราคาล่าช้า 15 นาทีจาก SIP       | ไม่มีงานเพิ่ม แต่ไม่ตอบสิ่งที่ขอ                                                                      |
| 2. ใช้ `latest` ของ IEX | ราคาล่าสุดจากตลาด IEX แห่งเดียว | ฟรี แต่อาจต่างจากราคาตลาดรวม หุ้นที่ซื้อขายน้อยบน IEX อาจไม่มีราคาหรือราคาเก่า ต้องติดป้ายว่าเป็น IEX |
| 3. SIP แบบ real-time    | ราคาตลาดรวมล่าสุด               | ต้องใช้แผนเสียเงิน ขัดกับข้อกำหนดของเฟสนี้                                                            |

frontend ไม่มีความเห็นว่าควรเลือกทางไหน เพราะเป็นเรื่องต้นทุนและสิทธิ์ของบัญชีผู้ให้บริการ
สิ่งที่ขอคือให้ผลการตัดสินใจสะท้อนอยู่ใน contract ตามข้อถัดไป

### สิ่งที่เสนอ (ไม่ขึ้นกับทางที่เลือก)

เพิ่มฟิลด์ใน `QuoteResponse` ที่บอกชนิดของราคา เพื่อให้ UI ติดป้ายจากข้อมูล ไม่ต้องเขียนข้อความตายตัว เช่น

| ฟิลด์           | ตัวอย่าง                              | ใช้ทำอะไร                                   |
| --------------- | ------------------------------------- | ------------------------------------------- |
| `price_type`    | `delayed_bar_close` \| `latest_trade` | เลือกข้อความ "ราคาล่าช้า" หรือ "ราคาล่าสุด" |
| `delay_minutes` | `15` หรือ `0`                         | แสดงว่าล่าช้ากี่นาที                        |

ฟิลด์ `feed`, `source`, `as_of`, `stale`, `session_status` ที่มีอยู่ใช้ต่อได้ตามเดิม
ถ้าเลือกทาง 2 ค่า `feed` จะเป็น `iex` และ UI จะแสดงว่าเป็นราคาจากตลาดเดียว

### ข้อควรระวัง

- ถ้าราคาเปลี่ยนเป็นราคาล่าสุด `unrealized_pnl` จะเปลี่ยนทุกครั้งที่โหลด ต้องตัดสินว่า cache 60 วินาทีเดิมยังเหมาะหรือไม่
- ราคานอกเวลาซื้อขายปกติ (pre-market, after-hours) จะปนเข้ามาหรือไม่ ต้องระบุใน `session_status`
- ข้อความใน Swagger ของ `valuation` ตอนนี้ระบุว่าเป็นราคาล่าช้า ต้องแก้ให้ตรงกับทางที่เลือก

## D. กราฟเทียบผลตอบแทนกับ S&P 500 และ Nasdaq-100

### ปัญหา

เจ้าของโปรเจกต์อยากเห็นในหน้า dashboard ว่า "พอร์ตเราชนะดัชนีหรือไม่" เทียบกับ S&P 500 และ Nasdaq-100
API ตอนนี้ให้มูลค่าพอร์ต ณ ขณะนี้เท่านั้น ยังขาดสามอย่าง

1. ราคาปิดรายวันย้อนหลังของหุ้นที่ถือ
2. ราคาย้อนหลังของตัวแทนดัชนี
3. วิธีคิดผลตอบแทนที่เทียบกับดัชนีได้ แม้ผู้ใช้จะซื้อเพิ่มหรือขายระหว่างทาง

ข้อนี้ตรงกับทิศทางของ ADR-0012 ที่ให้เฟสถัดไปเริ่มด้วย daily bars แบบ delayed
และ ADR นั้นกำหนดว่าต้องเสนอ timeframe ช่วงประวัติ และ method ของ `PriceProvider` ก่อนลงมือ ข้อเสนอนี้เป็นจุดเริ่มของการคุยเรื่องนั้น

### สิ่งที่ frontend ต้องการจาก API

endpoint ที่ตอบชุดข้อมูลรายวันพร้อมวาดกราฟเส้น เช่น
`GET /api/v1/portfolios/{portfolio_id}/performance?range=1y&benchmarks=SPY,QQQ`
และแบบรวมทุกพอร์ตสำหรับ dashboard (จะเป็น endpoint เดียวกันที่ไม่ระบุพอร์ต หรือแยก path ให้ฝั่ง backend เลือก)

```json
{
  "currency": "USD",
  "range": { "from": "2025-11-10", "to": "2026-11-09" },
  "method": "time_weighted",
  "is_demo": false,
  "portfolio": {
    "return_percent": "18.4",
    "points": [
      { "date": "2025-11-10", "market_value": "1000", "return_percent": "0" },
      { "date": "2025-11-11", "market_value": "1012.5", "return_percent": "1.25" }
    ]
  },
  "benchmarks": [
    {
      "symbol": "SPY",
      "label": "S&P 500 (SPY)",
      "return_percent": "12.1",
      "points": [{ "date": "2025-11-10", "return_percent": "0" }]
    }
  ]
}
```

- `return_percent` ของทุกเส้นเริ่มที่ 0 ในวันแรกของช่วง เพื่อวางซ้อนกันบนแกนเดียวได้
- ช่วงที่ต้องการ: 1 เดือน, 3 เดือน, 6 เดือน, ตั้งแต่ต้นปี, 1 ปี และตั้งแต่รายการแรก
- วันที่คิดมูลค่าไม่ได้เพราะขาดราคาของหุ้นบางตัว ต้องเป็น `null` หรือถูกเว้นไว้พร้อมเหตุผล ไม่ใช่ 0 (หลักเดียวกับ ADR-0020)
- วันที่เป็นวันทำการของตลาดสหรัฐฯ ส่งเป็นวันที่ (`YYYY-MM-DD`) ไม่ใช่ timestamp เพื่อไม่ให้เลื่อนวันตาม timezone ของ browser

### เรื่องที่ฝั่ง backend ต้องตัดสิน

**1. วิธีคิดผลตอบแทน**

ระบบนี้ไม่มียอดเงินสด เงินเข้าพอร์ตตอนซื้อและออกตอนขาย ถ้าใช้ "มูลค่าพอร์ตวันนี้เทียบกับวันแรก" ตรงๆ
การซื้อหุ้นเพิ่มจะดูเหมือนพอร์ตโต จึงต้องเลือกวิธีที่ตัดผลของเงินเข้าออก

| วิธี                                   | ตอบคำถามอะไร                                     | หมายเหตุ                                                                 |
| -------------------------------------- | ------------------------------------------------ | ------------------------------------------------------------------------ |
| Time-weighted return                   | "หุ้นที่เลือกทำผลงานดีกว่าดัชนีไหม"              | เป็นวิธีมาตรฐานสำหรับเทียบกับดัชนี ต้องตัดช่วงทุกครั้งที่มีรายการซื้อขาย |
| จำลองว่าเงินทุกก้อนไปซื้อ ETF ดัชนีแทน | "ถ้าเอาเงินเดียวกันไปซื้อดัชนี ตอนนี้จะมีเท่าไร" | เข้าใจง่ายสำหรับผู้ใช้ทั่วไป และรวมผลของจังหวะซื้อขายด้วย                |

frontend วาดได้ทั้งสองแบบ ขอแค่ให้ response บอกวิธีใน `method` เพื่อเขียนคำอธิบายใต้กราฟให้ตรง

**2. ตัวแทนของดัชนี**

เสนอใช้ ETF แทนตัวดัชนี คือ SPY สำหรับ S&P 500 และ QQQ สำหรับ Nasdaq-100 เพราะเป็น symbol ที่ผู้ให้บริการราคาหุ้นมีอยู่แล้ว
`label` ใน response ควรบอกชัดว่าเป็น ETF ไม่ใช่ตัวดัชนี

**3. เงินปันผลและ corporate actions**

- เฟส 1 ไม่บันทึกเงินปันผล ผลตอบแทนของพอร์ตจึงเป็นแบบไม่รวมปันผล
  ถ้าราคา ETF ดัชนีถูกปรับรวมปันผล (`adjustment=all`) ดัชนีจะได้เปรียบ จึงควรใช้ฐานเดียวกันทั้งสองฝั่ง และบอกใน response
- หุ้นที่แตกหุ้นในช่วงที่ถือจะทำให้เส้นของพอร์ตผิด เพราะระบบยังไม่รองรับ split ต้องตัดสินว่าจะแจ้งผู้ใช้อย่างไร

**4. การเก็บราคารายวัน**

- timeframe ที่เสนอคือ 1 วัน (ราคาปิดของ regular session)
- จะเก็บในตารางของแอปที่อ้าง `instruments` (ADR-0008) หรือดึงสดพร้อม cache เป็นเรื่องของฝั่ง backend
  ที่ต้องพิจารณาคู่กับโควตาของ provider และเวลาตอบของ endpoint
- มูลค่าพอร์ตย้อนหลังคิดได้จากการ replay รายการกับราคาปิดรายวัน ไม่จำเป็นต้องเก็บ snapshot รายวัน
  แต่การแก้รายการย้อนหลังต้องให้ผลกราฟเปลี่ยนตาม

**5. โหมดเดโม**

ผู้ให้บริการเดโมตอนนี้มีราคาคงที่ 8 symbol และไม่มี QQQ ถ้าจะให้กราฟทำงานในโหมดเดโม
ต้องมีชุดราคาย้อนหลังตัวอย่างและเพิ่ม QQQ โดย response ต้องมี `is_demo: true` เพื่อให้ UI ติดป้าย

### ฝั่ง frontend หลังได้ endpoint นี้

- กราฟเส้นในหน้า dashboard และหน้าพอร์ตด้วย TradingView Lightweight Charts ตามที่ `AGENTS.md` กำหนดไว้
- ปุ่มเลือกช่วงเวลา และข้อความสรุปว่าพอร์ตสูงหรือต่ำกว่าดัชนีแต่ละตัวกี่จุดเปอร์เซ็นต์ โดยใช้ `return_percent` ที่ API ส่งมา
- คำอธิบายใต้กราฟ: วิธีคิดตาม `method`, ไม่รวมเงินปันผล, ราคาเป็นราคาปิดรายวัน และไม่ใช่คำแนะนำการลงทุน

frontend จะยังไม่เริ่มส่วนนี้จนกว่า contract จะอยู่ใน `swagger.json`

## นอกขอบเขตของข้อเสนอนี้

Market cap, P/E, % เปลี่ยนแปลงรายวัน, โลโก้บริษัท และการค้นหาบริษัท ไม่ได้ถูกขอในรอบนี้และไม่อยู่ในข้อเสนอ

## งานฝั่ง backend (ถ้ารับ)

- **A:** เพิ่มฟิลด์ใน DTO และ service ของ valuation พร้อม test กรณี `null` (ราคาไม่ครบ, ขายหมด, ต้นทุนเป็น 0)
- **B:** service และ handler ใหม่ พร้อม test การรวมหุ้นข้ามพอร์ต, `coverage` ผสม และการแยกผู้ใช้
- **C:** ADR ใหม่ถ้าเปลี่ยนแหล่งราคา, ฟิลด์ชนิดราคาใน `QuoteResponse`, แก้คำอธิบายใน Swagger
- **D:** ADR ใหม่ต่อจาก ADR-0012, method ราคารายวันใน `PriceProvider` ทั้ง Alpaca และ demo, ที่เก็บราคา (ถ้าเลือกเก็บ),
  service คิดผลตอบแทนพร้อม test กับรายการย้อนหลัง
- ทุกข้อ: อัปเดต swagger annotations แล้ว generate ใหม่ และแก้ `docs/frontend-handoff.md` หัวข้อ 1, 4 และ 8

## คำถามที่ต้องการให้ฝั่ง backend ตัดสิน

1. รับข้อ A ไหม และ `_percent` จะเป็นหน่วยเปอร์เซ็นต์หรืออัตราส่วน
2. รับข้อ B ไหม หรือให้ dashboard แสดงทีละพอร์ตโดยไม่มียอดรวม
3. ข้อ C เลือกทางไหน และจะเพิ่มฟิลด์ชนิดราคาใน `quote` หรือไม่
4. ข้อ D อยู่ในเฟสถัดไปตาม ADR-0012 ใช่ไหม ใช้วิธีคิดผลตอบแทนแบบใด และใช้ SPY/QQQ เป็นตัวแทนดัชนีได้หรือไม่
5. ลำดับที่อยากทำ: frontend เสนอ A ก่อน เพราะเล็กที่สุดและผู้ใช้ถามถึงโดยตรง แล้วตามด้วย B, C และ D

---

ข้อ A และ B ไม่เร่งด่วนในแง่ความถูกต้อง เพราะหน้าพอร์ตปัจจุบันแสดงยอดเงินได้ครบและไม่มีตัวเลขที่ผิด
ที่เสนอมาเป็นเรื่องให้ผู้ใช้อ่านพอร์ตได้ง่ายขึ้น ส่วนข้อ C และ D เป็นการขยายขอบเขตจากเฟส 1
ถ้าฝั่ง backend เห็นว่าควรรอ frontend ใช้หน้าปัจจุบันต่อได้โดยไม่ต้องแก้อะไร
